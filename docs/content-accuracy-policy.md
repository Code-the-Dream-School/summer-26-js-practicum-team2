# Content Accuracy Review Policy

### Accuracy Reviewer Role

The role of the accuracy reviewer is to confirm that content in our project is factually correct, is complete, and consistent within a reasonable constraint. Because this is a educational demo application never intended for production, we can be more laxed that if it were deployed to actual users. This role is created more as a formality to meet the criteria of our user story

### Who do we define as the content reviewer?

Anybody on our team can be designated as an accuracy reviewer. We should absolutely utilize the guidance of our mentors to sign off on content to ensure that we receive direct feedback if we miss something. Also, if we know anybody in the financial industry that are willing to help, they may prove to be an asset to the content review team. Even though no single team member is assigned to this role, it is worth noting that our curriculum was primarily written by [@kwishart24](https://github.com/kwishart) and [@BytesOfStrength](https://github.com/BytesOfStrength). As the author of this policy, I would like to acknowledge and thank them for their efforts.

### Requirements for sign-off

- Before we make any chages to the content, at least one team mate must approve content before publishing it.
- Our mentors are availabel to review and sign off on project content, especially if the content reflects course standard or program information.
- If possible, reach out to your friends or family, especially if they have any ties to the financial industry to review content.
- Content cannot be marked accurate if a reviewer hs not approved it.

See the review checklist: [Content Accuracy Checklist](./content-accuracy-checklist.md)

### Named reviewer list

Use the following format to record who has reviewed the content:

- Mentor reviewer: [Name or GitHub Handle]
- Qualified third-party reviewer: [Name or GitHub Handle / Organization (or Industry) / Qualification]
- Additional reviewer (if needed): [Name or GitHub Handle]

This will help us make sure the review record is clear and accountable, as well as being compliant with this content accuracy review policy

### Corrections workflow for reported content issues

When somebody identifies an issue in published lesson content, we treat it as a content-issues fix item rather than a casual note.

#### Required GitHub workflow

- Create a GitHub issue labeled `content-issues`
- Add the issue to the team backlog in JIRA where it can be tracked
- Assign an owner for the issue
- The issue is reolved through this flow: Report -> Fix -> Assign Owner -> Fix/Close Issue

#### Assigned Owner

- A designated team member is assigned as the owner of the issue
- The owner is tagged at time of issue creation
- This owner is responsible for reviewing the issue and resolving it in a timely manner

#### Service-level agreement (SLA)

- Content issues that are reported must be acknowledged promptly and assigned within the same day if possible
- Corrections should be made with three business days of issue creation, unless it requires external review or a larger change to the curriculum
- If it is not possible to fix within the SLA then the owner must document the reason and the expected next step to resolve it

#### Resolution record

- A reolved issue should include a clear summary of what was incorrect
- The correction or update should be linked to the relevant content change or PR
- Resolution should be documented in the issue or merged PR so taht the history is available for future review

This workflow is intended to keep us accountable for accuracy, ensuring small inaccuracies are identified quickly, and it gives every reported problem a clear owner and completion path.
